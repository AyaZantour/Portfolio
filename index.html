Case study 1

IASMO, the AI layer inside Smoft ERP

IASMO lives inside Smoft ERP. It's a set of specialised agents, each good at one kind of task, with a Supervisor in front deciding who handles what.

Organisation
Smoft ERP, Sousse
My part
SmartOCR (design & build), Supervisor, improvements to other agents incl. AutoFlow, model deployment
Period
Feb 2026 – present
Context

ERP users deal with a lot of different tasks: scanned supplier invoices, CVs for open positions, documents that need to become records in the system, and many others. One model with one huge prompt is a poor fit for that range. IASMO splits the work into specialised agents that each have their own logic, prompts and tools. A Supervisor sits in front of them and decides which agent should handle each request.

Agents are orchestrated with LangGraph. The language models run on the company's own GPU servers rather than through an external API. That shapes much of the engineering, from context size to latency to which models are viable.

The ecosystem
My contribution
  • SmartOCR: designed and built as my final-year project, now evolving with a vision-language model. Case study 2 →
  • AutoFlow and other agents: took part in improving the other IASMO agents. On AutoFlow, that work involved bringing Kafka into its architecture.
  • Supervisor: worked on the routing concept and implementation, focusing on reducing prompt size with retrieval. Case study 3 →
  • Model serving: deploying LLM and VLM inference services with vLLM on multi-GPU Linux servers. Case study 4 →
  • The ERP itself: tickets, debugging and tests on PHP/MySQL features, so that AI features land in a product I understand from the inside.

IASMO is a team effort. I describe in detail only the parts I designed or worked on most deeply. Agents I didn't touch appear by name only.

Case study 2

SmartOCR reads and checks business documents

An IASMO agent that takes an uploaded document, works out what it is, extracts the fields the ERP needs, and checks them before anything becomes a record.

Role
AI engineering intern, final-year project (PFE)
Period
Feb – Jul 2026, continued since
Core stack
PaddleOCR, Qwen3-14B, Qdrant, BGE-M3, MySQL
Problem

Companies using an ERP still receive much of their paperwork as PDFs and scans: invoices, quotes, delivery notes and other documents. Someone has to identify each one, type its contents into the system and catch the mistakes. The mistakes matter most. A transposed digit in a bank account or a total that doesn't match its line items can create real accounting problems.

The goal of SmartOCR was to automate this inside the ERP. Classify the document, extract structured fields, and flag what looks wrong before a draft is confirmed.

    Measured during the final-year project, with the PaddleOCR + Qwen3-14B + RAG pipeline. Since joining full-time, I've been working on the next version, which uses a vision-language model to read documents.

    Read the engineering detailsapproach · the full rule set · what I learned
    Approach

    OCR and language model as separate steps

    PaddleOCR handles reading the page. Qwen3-14B handles understanding it: what kind of document this is and which value belongs in which field. Keeping the two separate lets each part be evaluated and replaced on its own. That turned out to matter later, when the reading step moved to a vision-language model, PaddleOCR-VL 1.6.

    Retrieval for business context

    Raw OCR text often isn't enough to classify a document reliably or to resolve ambiguous fields. I added a RAG layer: content is embedded with BGE-M3, indexed in Qdrant, and combined with contextual data from MySQL. Relevant context is retrieved and given to the model alongside the document, which improves classification and extraction.

    Validation as a first-class stage

    Extraction accuracy is never 100%, so the system has to say when it is unsure or when the numbers don't hold together. The validation layer checks extracted data before it reaches an ERP draft. It's configurable, because different companies and document types need different rules.

    Validation & anomaly detection
    CheckWhat it catches
    Duplicate detectionThe same document submitted twice, before it can be recorded twice.
    HT / TVA / TTC consistencyAmounts that don't reconcile: pre-tax total (HT) plus VAT (TVA) should equal the tax-inclusive total (TTC).
    RIB validationProblems in the bank account identifier (RIB) found on the document.
    Price validationPrices that look inconsistent or suspicious.
    Required fieldsDocuments missing fields the ERP needs to create a valid record.
    Draft-stage blockingIssues are raised at the draft stage, and a failing check can block the draft from going further.
    Configurable rulesChecks can be adjusted instead of being hard-coded for a single document format.
    Performance loggingEach processing stage is logged, so slow or failing steps can be found and measured.
    What I learned
    • For business documents, the extraction model is only half the system. The validation around it decides whether the output can be trusted.
    • Retrieval isn't only for chatbots. Giving the model the right business context made it better at understanding documents.
    • A modular pipeline pays off. Because reading and understanding were separate stages, moving to a VLM was an upgrade rather than a rewrite.
    Case study 3

    The Supervisor picks the right agent, without a huge prompt

    How do you build an orchestrator that makes good routing decisions while keeping prompt size, cost and latency under control?

    Role
    Concept and implementation work on routing
    Orchestration
    LangGraph
    Model
    Qwen3-14B, self-hosted
    Problem

    Every request to IASMO goes through the Supervisor first, so its quality and speed affect everything behind it. A wrong route sends the user to an agent that can't help. A slow route adds latency to every single interaction.

    The Supervisor also needs to know about the agents it routes to. The simple approach is to put all of that knowledge in the prompt on every call. That works with two agents. With eight or more, the prompt grows with every capability added, and on a self-hosted 14B model those tokens are paid for in GPU time on every request.

    Routing, live
    Engineering the context
    First approach: send everything
    system instructions all agent descriptions all routing rules & examples long conversation context user request

    Simple and predictable, but the prompt is large on every call and keeps growing as agents are added. Most of it is irrelevant to the request at hand.

    Revised approach: retrieve what's relevant
    system instructions all agent descriptions retrieved: relevant routing context compact request state user request

    Routing knowledge is retrieved per request (RAG) instead of being sent in full every time. The prompt stays focused, and adding an agent no longer makes every call heavier.

    Read the engineering detailsdesign decisions · what I learned
    Decisions
    • Treat tokens as a budget. On self-hosted hardware, prompt size directly affects latency and how many requests a GPU can serve. That's why prompt and token optimisation became a core part of the Supervisor's design rather than a final cleanup.
    • Use a graph, not a chain. LangGraph makes the routing state and transitions explicit, which makes it easier to see why a request went where it did and to add new agents.
    • Send attachments to the specialist. Files go to SmartOCR, which already has a document pipeline, rather than being parsed again inside the Supervisor.
    What I learned

    Orchestration is mostly a context-management problem. A routing model only needs to know enough to choose well, and deciding what that means for each request is where most of the engineering goes.

    Case study 4

    Running the models ourselves: vLLM, GPUs and the services around them

    I'm an AI engineer, not a DevOps engineer. Still, our agents run on our own GPUs, so understanding the server under the model has become part of my job.

    Hardware
    Multi-GPU Linux servers, NVIDIA L4
    Serving
    vLLM (LLM & VLM inference), systemd
    Around it
    FastAPI, RabbitMQ, Redis, Kafka, Qdrant, MySQL
    What I do
    • Deploy inference services with vLLM for both language models (such as Qwen3-14B) and vision-language models (PaddleOCR-VL), on multi-GPU servers with NVIDIA L4 cards.
    • Run models as managed services. Each one runs as a systemd unit, so it's managed like any other system service: started, stopped, restarted and inspected with standard Linux tooling.
    • Keep several AI services side by side, each on its own port, organised so agents know where to find the model they need.
    • Experiment before committing. I try candidate models and configurations on the actual hardware before a deployment decision is made.
    Where it fits
    Why it matters

    Many decisions that look like modelling choices are really infrastructure constraints. A model's size determines whether it fits on an L4 next to another service. Context length affects memory and throughput. Whether two agents can share a model depends on how it is served. Seeing those constraints first-hand changed how I design agents: I think about prompt size, concurrency and serving cost while designing, not after deployment.

    Semantic search over agro-industrial enzyme documentation

    A RAG system that lets people ask questions in plain language over a corpus of technical data sheets for food-industry enzymes, instead of searching PDFs by keyword. Every answer cites its source document with a similarity score.

    How it’s built

    What I built

    • The full pipeline: PDF extraction, chunking with overlap that respects sentence boundaries, embeddings, cosine-similarity retrieval and LLM answer synthesis.
    • A Flask REST API (POST /search) and a web interface for querying.
    • A persisted vector index (.npz + JSON), so documents aren't re-embedded on every start.

    Decisions

    • all-MiniLM-L6-v2 (~80 MB) so the whole index runs on a CPU.
    • Plain NumPy instead of a vector database, which is enough at this corpus size.
    • Search-only fallback: without an LLM key it still returns ranked sources.

    SmartParkTN reads Tunisian licence plates

    Generic ALPR systems fail on Tunisian plates because of the Arabic word «تونس» between the digit groups. SmartParkTN reads plates in real time, decides on access, computes parking fees, and includes a RAG assistant that answers staff questions about parking rules.

    How it’s built

    What I built

    • A 5-stage pipeline: YOLOv8n plate detection → 6 preprocessing variants (CLAHE, Otsu, adaptive thresholding, deskewing…) → bilingual OCR → normalisation → access decision.
    • Two PaddleOCR instances (Latin and Arabic) whose results are merged. A dictionary of 12 common misreadings of «تونس» maps them all to TN.
    • Access rules per vehicle category and a billing engine (grace period, hourly rate, daily cap).
    • A French-language RAG assistant built on ChromaDB and a multilingual embedding model.

    Decisions

    • Character corrections (O→0, S→5, B→8…) apply only to numeric positions, so they can't corrupt TN/RS.
    • Plates are validated against regex patterns before any database lookup.
    • The assistant falls back to retrieval-only answers when no LLM is available.

    My approach

    How I like to work

    01

    Start from the workflow, not the model.

    SmartOCR began with a question about invoices: what does an accountant need to trust an extracted total? The answer, consistency checks and blocking at the draft stage, shaped the system more than the choice of model did.

    → SmartOCR validation layer

    02

    Treat context as a budget.

    On self-hosted models, every token costs GPU time. I'd rather retrieve the three things a model needs than send it thirty and hope it ignores the rest.

    → Supervisor context retrieval

    03

    Plan for the model being unavailable.

    My projects tend to have a fallback: search-only mode when the LLM isn't reachable, full-frame OCR when the detector misses. A system that degrades gracefully is easier to trust.

    → RAG search fallback, SmartParkTN

    04

    Know the layer below.

    I learned vLLM, systemd and GPU memory limits because the agents I design run on them. Understanding the server makes me better at designing what runs on it.

    → Model serving at Smoft
